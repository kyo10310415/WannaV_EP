# パスワード再設定用メールアドレス登録

## 今回の範囲

- 新規・既存を問わず、有効化後のログイン時に未登録者をメール登録画面へ案内する。全ロール対象。
- 初回パスワード変更が必要な場合は、変更してからメール登録へ進む。
- 学籍番号・ログインID・内部用users.emailは変更しない。受信確認済みのアドレスは専用テーブルへ保存する。
- 登録画面に「パスワード再設定用」であることを明記する。
- 確認済みメールを登録した利用者は、ログイン画面の「パスワードを忘れた方はこちら」から自身で再設定できる（別途有効化が必要）。

## 本番の有効化前に必要な設定

既定では無効。メールの送信設定・受信テスト・十分な送信枠を用意するまで、`RECOVERY_EMAIL_ENROLLMENT_ENABLED=true` にしない。

### Google Workspace（今回の推奨構成）

既存の会社メールアカウントと、そのアカウントで発行したアプリパスワードを使う。Resendのドメイン認証やDNSレコード追加は不要。有料のRender Web Serviceで使用する（無料Web ServiceはSMTPの465/587ポートへの接続が禁止されている）。

Renderの対象Web Service → Environmentに以下を設定し、Save and deployで適用する。

```dotenv
RECOVERY_EMAIL_PROVIDER=google_workspace
GOOGLE_WORKSPACE_SMTP_USER=<アプリパスワードを発行した会社メールアドレス>
GOOGLE_WORKSPACE_APP_PASSWORD=<発行した16文字のアプリパスワード>
RECOVERY_EMAIL_FROM=<GOOGLE_WORKSPACE_SMTP_USERと同じメールアドレス>
RECOVERY_EMAIL_ENROLLMENT_ENABLED=false
RECOVERY_EMAIL_DAILY_LIMIT=90
```

- アドレスは実在するGoogle Workspaceアカウントを指定する。表示名・山括弧は入力しない。未作成のnoreplyアドレスや別アカウントのアドレスを指定しない。
- パスワードは通常のGoogleログインパスワードではなく、発行したアプリパスワード。表示時の区切りの半角スペースはアプリ側でも取り除く。秘密情報をチャット・Git・画面画像・ログへ載せない。
- サーバーはsmtp.gmail.com、465、暗号化TLSに固定。証明書検証は無効にしない。SMTP_HOST/SMTP_PORTなどの追加設定は不要。
- RECOVERY_EMAIL_PROVIDER未指定時は従来のresendを使う。google_workspace選択時にはRESEND_API_KEYは不要で、残っていても使用しない。不備・失敗時の自動フォールバックや自動再送はしない。
- 初回設定ではfalseのまま保存する。trueにすると全ロールの未登録ユーザーが次のログイン時から登録必須になる。受信確認には一時的にtrueとして担当者自身で再ログインし、登録→コード受信→確認完了を試す必要がある。その間ほかの未登録者も対象になるため、利用の少ない時間帯に行う。受信できない場合は直ちにfalseへ戻して再デプロイする。falseの間、登録APIからは送信しない。
- 日次上限90はGoogle側の保証枠ではなく、アプリ独自の安全上限。既存ユーザーが集中すると上限後に登録を完了できない。全体展開前に利用人数に見合った上限を検討する。Google側の制限はアカウント・契約・試用状態によって異なり、同じアカウントからの通常メール送信とも共有される。
- Googleのログインパスワード変更でアプリパスワードが失効した場合は、再発行してRenderを更新する。認証失敗時は会社のGoogle Workspace管理ポリシーも確認する。
- SMTP受理は受信箱への到達保証ではない。迷惑メールフォルダーも含め、実受信まで確認する。SMTPにはResendのような冪等送信保証がないため、タイムアウト時は重複の可能性を考慮して自動再試行しない。再送すると以前のコードは無効になる。

公式設定：https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app

### Resend（既存構成を維持）

1. Resendのアカウントを作成する（契約・規約への同意は運用担当者が行う）。
2. Domainsに `portal-mail.oneloopinc.net` を追加し、Resendが表示するDNSレコードをDNS管理画面へ追加する。既存のルートドメインのメール設定・MXを置き換えない。
3. ドメイン認証の完了を確認する。送信元は `noreply@portal-mail.oneloopinc.net` を想定する。
4. 当該ドメインの送信だけに権限を限定したAPIキーを発行し、Renderへ設定する。秘密情報をチャット・Git・画面画像へ載せない。
5. Resend側の送信テストで実際に受信できることを確認する。
6. 送信枠とアプリ側上限を合わせてから登録必須化を有効にし、担当者のアカウントで実際の登録完了まで確認する。

```dotenv
RESEND_API_KEY=<Resendの送信専用APIキー>
RECOVERY_EMAIL_PROVIDER=resend
RECOVERY_EMAIL_FROM=noreply@portal-mail.oneloopinc.net
RECOVERY_EMAIL_ENROLLMENT_ENABLED=false
RECOVERY_EMAIL_DAILY_LIMIT=90
```

Resend無料枠は1日100通。アプリ既定は他の送信や再送の余裕を残すため日本時間の1日90回。失敗・結果不明も送信試行として数える。既存の未登録者が集中すると上限後は登録を完了できないため、全体展開前に利用人数と送信枠を確認する。有料プランは別途承認後に契約する。

## 安全性・運用

- コードは暗号学的乱数の6桁・有効期限10分。DBにはJWT_SECRETを使う用途別HMACだけ保存し、コードの平文を保存・ログ出力しない。
- 受信確認が成功するまで、登録済み扱いにしない。コード5回失敗で当該コードを無効扱いにする。
- 再送は60秒間隔、本人1日5回、全体は設定上限。DB内のロックで同時要求を制御する。
- 送信エラー時は当該コードを無効化し、自動再送しない。事業者のエラー本文やAPIキーを利用者へ返さない。
- 登録操作にはログイン後15分以内の認証を要求し、管理者によるPWリセット等で失効したセッションは拒否する。
- 受信確認後は登録必須クレームのないトークンを発行する。確認済みのコードを再送信してもトークンの再発行はしない。
- 確認済みアドレスをこのAPIで上書きすることはできない。アドレス変更は今回の対象外。
- 有効化前からログイン中のセッションは突然遮断しない。ログインし直した際に発行するトークンから登録案内を開始する。
- 有効化後に発行した登録待ちトークンは、登録完了まで通常の保護API・メディアへ進めない。登録用APIは支払い制限と切り離して本人が登録できるようにするが、ポータルへの既存の支払い・権限判定は変更しない。
- 登録済みの利用者は次回以降のログインで登録画面をスキップする。
- 確認済みメールがない状態ですでにPWを忘れている利用者は、従来の管理者リセットでログインを復旧してから登録する。
- 初期PWを全員1111とする既存運用は変更していない。学籍番号と初期PWを知る第三者の先行ログインをメール登録だけで防ぐことはできないため、将来の個別招待方式を検討する。

## 障害時・戻し方

- メール送信障害や上限で登録が進まない場合は、まず送信元・枠・配信状況を確認する。
- 緊急時は `RECOVERY_EMAIL_ENROLLMENT_ENABLED=false` で登録必須化を解除できる。認証・権限・PW変更・既存の管理者リセットは維持する。
- DB変更は専用2テーブルと索引の追加だけ。既存ユーザー情報やPWは更新しない。旧版へ戻す場合も追加テーブルを削除する必要はない。
- 受信済みアドレスは個人情報。DBアクセスを必要な担当者に限定し、別目的で利用しない。

## 本人によるパスワード再設定

既存のGoogle WorkspaceまたはResendの送信設定に、以下を追加する。メール登録の必須化とは独立した設定で、初期値は無効。

```dotenv
PASSWORD_RESET_ENABLED=true
PASSWORD_RESET_ORIGIN=https://wannav-ep.onrender.com
```

`PASSWORD_RESET_ORIGIN`は実際に利用者がログインする信頼済みHTTPSのオリジン（パス・クエリ・フラグメントなし）。独自ドメインを使っている場合はそちらを指定する。リクエストのHostや転送ヘッダーからURLを生成しない。ローカルの隔離テストのみ、非productionでlocalhost/127.0.0.1のHTTPを許可する。

### 操作手順

1. ログイン画面の「パスワードを忘れた方はこちら」を開く。
2. ログインIDと、アプリ内で受信確認済みのメールアドレスを入力する。同じメールを複数アカウントで使っていても、対象を特定する。
3. 届いたメールのリンクを開く（有効期限15分）。
4. 新しいパスワードを2回入力して確定する。8文字以上、bcryptの切り詰めを防ぐためUTF-8で72バイト以内。この画面以外の既存PW変更条件は変更しない。
5. ログイン画面に戻り、新しいパスワードでログインする。ログインID・権限・学習履歴は変更しない。

メール未登録・受信できない場合は管理者に依頼する。アカウント存在、不一致、未確認メール、送信上限の違いは申し込み画面の応答で明かさない。メール到達を保証する「送信しました」表示にはしない。
登録直後や再送時の60秒待機は、入力画面と共通の申込後メッセージの両方に明記する。実際にそのアカウントへ直前に送ったかどうかで応答を変えると存在確認に悪用されるため、制限対象だけを特定した応答は返さない。

### 保護と運用上の制限

- 32バイトの暗号学的乱数トークンを使い、DBには用途別HMACのみ保存する。一度使用すると破棄する。最新リンクを発行すると古いリンクは無効になる。
- メールのリンクはフラグメントにトークンを持ち、サーバーのURL・アクセスログには送らない。画面起動時にURLから除去してメモリだけで保持する。再読込時はメールのリンクを開き直す。Referrer-Policy:no-referrer、no-store、外部リソースを許可しないCSPを設定する。
- 正当なトークンの検証・PW更新・リンク破棄・セッションnonce変更は同じDBトランザクションで実行し、同時実行でも成功は1回だけ。既存のnonce照合で旧JWT・メディア用Cookieも失効する。自動ログインはしない。
- 管理者リセット、通常のPW変更、確認済みメールの変更後は、発行済みリンクを拒否する。申し込んだだけでは現在のPWやセッションを無効にしない。
- 送信はメール登録と共通の日本時間日次上限（既定90）・本人1日5回で制御し、申込メールは60秒間隔。失敗や結果不明も送信試行として数える。再設定完了の通知も同じ送信枠を使用し、上限・配信障害時の通知失敗は完了済みPW変更を取り消さない。
- DBにHMAC化したIP・入力組み合わせの15分レート制限を持つ。IP毎・エンドポイント毎100回、申込入力組み合わせ毎5回。trust proxyを広く有効化せずreq.ipを使うため、リバースプロキシ構成によっては同じプロキシ経由の利用者がIP枠を共有する。生のIPや入力ID・メールを制限テーブルへ保存しない。古い制限行は1時間経過後に順次削除する。
- 申し込みへの応答はアカウント検索・SMTP送信より先に返し、アカウントの有無によるSMTP応答時間の差を公開しない。バックグラウンド送信は各プロセス同時5件までで、それ以上はアカウントによらず一時的な混雑を表示する。再起動をまたぐ永続ジョブキューや自動再送は追加していない。配信されなければ60秒以上待って再申し込みする。
- 送信失敗時は当該リンクを無効化する。エラー・トークン・PW・宛先をログへ表示しない。運用ログは固定の失敗メッセージだけとする。
- 公開API：`POST /api/auth/password-reset/request`（loginId,email）、`POST /api/auth/password-reset/complete`（token,newPassword,confirmPassword）。トークンで通常のAPIへアクセスすることはできず、成功時にJWTを発行しない。

無効化は`PASSWORD_RESET_ENABLED=false`で再デプロイする。メール登録・既存ログイン・管理者リセットには影響しない。DB追加は`password_reset_tokens`と`password_reset_rate_limits`の2テーブルのみ。ロールバック時も削除は不要で、既に変更されたPWを旧PWへ戻すことはできない（必要なら既存の管理者リセットを使う）。

自己再設定の検証（2026-11-13）：Node.js 22.23.5の全体回帰283件成功（スキップ0）。その後に追加したメール文面テストを含む送信テスト5件も成功。隔離ブラウザではログイン画面の入口→ダミー宛先申し込み→リンク先フォーム、390px/1280pxで横はみ出しなし、URLからのトークン除去、再読み込み時の案内を確認。PW更新・同時再設定・全ロール維持・旧セッション失効は隔離DBの自動テストで検証。実メール配信と本番での本人操作は未検証。
