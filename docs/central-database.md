# 中央管理DB連携

ポータルのDATABASE_URLは変更しない。中央管理システムのDBへ別Pool（最大2接続）で読み取り専用接続し、ポータルDBにキャッシュする。画面表示のたびに外部DBへ接続しない。後からの項目追加はcentralDatabase.jsの明示SELECTとcentralStudentSync.jsの変換、必要なキャッシュ/API/表示に追加する。支払い情報・パスワード等をSELECT *で持ち込まない。

## Render設定

Web ServiceのEnvironmentへ設定する（秘密のURLをチャットやGitへ貼らない）。

```
CENTRAL_STUDENT_SYNC_ENABLED=true
CENTRAL_DATABASE_URL=<中央管理DBの読み取り専用ユーザーの接続URL>
CENTRAL_DATABASE_SSL=true
```

同じRenderワークスペース・リージョンのWeb ServiceとDBではInternal Database URLを使い、CENTRAL_DATABASE_SSL=falseに設定する。External Database URLではtrueとしてTLS証明書を検証し、ネットワーク許可も確認する。外部接続で証明書エラーが出る場合は接続ホスト・CA設定を確認し、無条件に検証を無効にしない。falseはRenderの内部プライベートネットワークか信頼できるローカル開発用のみ。

中央DB管理者が専用ユーザーにpublicスキーマのUSAGEとstudents/tutors/lessonsのSELECTだけを付与する。DDL、INSERT、UPDATE、DELETE、所有者権限は不要。アプリもdefault_transaction_read_only=onとREPEATABLE READ READ ONLYで取得する。本作業ではユーザー作成や本番DB操作を実施していない。

有効時は起動時＋毎時00分（日本時間）に同期し、直接Notion同期は停止する。生徒管理画面の同期ボタンも中央管理DBへ切り替わる。falseにすると従来のNotion連携に戻るが、変更済みキャッシュは次のNotion同期まで残る。支払いスプレッドシートの毎時同期とアクセス判定は変更しない。

## 取得項目 / 保持するもの

- students: 学籍番号・生徒名・ステータス・契約プラン・担当Tutor・Notion参照・レッスン開始日・X/YouTube ID。
- tutors: 名称とメールを担当者照合にだけ利用する。
- lessons: 当月以降（未来を含む）の予約ID・学籍番号・担当Tutor・日時・時刻・タイトル。過去月の履歴、会議URL、説明は今回は取得しない。

既存のNotionキャッシュとアカウント紐づけを再利用する。Notion ID（ハイフン差を吸収）または学籍番号で既存行を照合し、曖昧なら同期を中止する。Notion IDなしの新規行はcentral:学籍番号を内部キーにする。全契約状態を更新し、新規アカウント作成は従来の6プランだけ。学籍番号・初期PW1111・初回変更必須の既存仕様を維持する。

アカウントID・パスワード・手動設定したログインID・学習進捗・小テスト・キャラクター・支払いデータは保持する。学籍番号やNotion IDを同時に変更した場合は自動照合できないため、管理者が移行前に対応を確認する。

中央Tutor名を中央tutorsのnotion_name/name/tutor_nameへ照合し、メールが一致するポータルのスタッフアカウントが一意の場合に担当者IDを設定する。未一致/重複は未割当とし、クルーへ誤った生徒を開示しない。担当名はそのまま表示する。クルー閲覧を使う場合はスタッフの登録メールの一致を事前確認する。

生徒管理画面に予約状況ボタンを追加し、当月以降を50件ずつ表示する。管理者・セールスは全生徒、クルーは担当生徒のみ。生徒本人向けの予約表示や既存受講スケジュールへの自動転記は行わない。

## 同期安全性 / 制限

外部取得失敗・0件・重複等では前回データを保持する。同時手動/自動同期は同じPromiseを共有する。予約キャッシュ置換・担当者更新・同期成功時刻はローカルトランザクションで更新する。中央DBの予約削除は次の成功同期でキャッシュに反映する。中央DBに存在しないキャッシュ生徒（初回切替時の旧Notion行も含む）は「同期対象外」にし、アカウントや進捗は削除しない。初回同期前に中央DBの生徒が網羅されていることを確認する。

生徒UPSERT/アカウント作成は既存の分割処理を再利用し、その後予約等を保存する。後半でDB障害が発生した場合、生徒情報だけ更新済みになることがあるが、予約は前回値・成功時刻は前回のまま。再同期で回復する。複数Web Serviceインスタンス間の同期ロックは今回未対応（単一インスタンス運用前提）。

ロールバックはCENTRAL_STUDENT_SYNC_ENABLED=falseとして再デプロイする。追加キャッシュの破壊的削除や中央DBへの書き戻しは不要。Notion情報へ戻す場合は設定を確認して明示同期する。

## 本番確認

1. バックアップ後、接続URLを設定して有効化。最初は検証環境で少数データを照合する。
2. 同期後、学籍番号・人数・状態・プラン・開始日・SNS ID・担当Tutorと予約を中央管理画面と比較する。
3. 既存ログイン、動画進捗、キャラクター、支払いアクセスが維持されることを確認する。
4. 未認証/他担当クルーから予約情報を読めないことを確認する。
5. 中央DB停止時も画面が前回キャッシュで使え、成功時刻が更新されないことを確認する。

本番の接続・実データ照合は環境変数設定後に必要。資格情報や個人データはエラーログへ出力しない。

開始日は読み取りトランザクション内のSET LOCAL DateStyleをISOに固定してtextとして取得する（DATE型・文字列型の両方に対応）。文字列は年先頭のYYYY-MM-DDまたはYYYY/MM/DDを受理し、月日1桁もゼロ埋めしてYYYY-MM-DDへ統一する。NULL・空欄は未設定として保持する。月日先頭など曖昧な形式、infinity、存在しない日付はINVALID_DATEとして拒否する。元DBの値・永続設定は変更しない。

## 開始日の診断

年先頭の日付に続く日時（Tまたは空白区切り、時分・秒・小数秒、Zまたは数値オフセット）も受理する。日時をUTCへ変換せず、記載された年月日を開始日として保持する。時間・オフセットの範囲と実在する日付を検証し、単なる先頭10文字切り取りで不正値を受理しない。

INVALID_DATE時はRenderログの「Central student start date diagnostics」に拒否された形式別件数を表示する。DATE_WITH_TIME（日時付き）、SLASH_DATE_WITH_TIME（スラッシュ形式・日時付き）、JAPANESE_DATE（年月日表記）、YEAR_MONTH_ONLY（年月のみ）、DAY_OR_MONTH_FIRST（月日順が曖昧）、INVALID_CALENDAR_DATE（存在しない日付）、INFINITY、OTHERに分類する。日付値・名前・学籍番号は出力しない。診断だけでは日付を補完・変換せず、保存前に同期を中止して既存データを保持する。

## 生徒照合の診断

Renderログ「Central student identity diagnostics」は複数候補がある中央生徒数（affectedStudents）と種類別件数（types）のみを出力する。NOTION_ID_DUPLICATEは正規化したNotion IDが複数一致、STUDENT_NUMBER_DUPLICATEは学籍番号が複数一致、NOTION_NUMBER_CONFLICTは各キーが1件ずつ一致するが別レコードを指す状態。その他はMULTIPLE_MATCHES。1人が複数種類に該当する場合があるため種類別件数の合計は人数と一致しないことがある。名前・学籍番号・Notion ID・元データは出力しない。候補を選択・統合・削除せず、当該生徒を更新保留する。

## 生徒ダッシュボードの当月レッスン

エントリープラン以外の生徒に中央予約キャッシュから本人の当月予約（日付・時刻・Tutor）を表示する。GET /api/central/my-lessonsはJWTの本人IDだけを使い、学籍番号などクライアント指定は無視する。日本時間で当月を計算し、過去に実施した当月予約も回数に含む。0回は赤、1回は黄色で予約案内を表示する。前日にアプリを開くと翌日の予定を大きなポップアップで表示する（開くたびに表示、重要メッセージ等の閉じ待ち）。月末は翌月1日の予約も前日通知対象。プラン未設定・エントリーは非表示。未同期・月替わり未同期・中央未連携・学籍番号重複では0回と判定せず確認不可を表示する。表示は毎時同期のキャッシュであり、キャンセル等は次回同期まで反映されない。

複数の既存候補がある中央生徒のみ更新を保留し、他の生徒は同期する。保留候補の情報・アカウント・担当・中央紐付け・予約キャッシュを保持し、同期対象外にも変更しない。手動同期結果に保留人数を表示する。元データ自体の重複や他の検証エラーは引き続き全体を停止する。保留候補と更新候補が同じNotionレコードを指す場合も安全のため停止する。

管理者・セールスは生徒管理ページの「学籍番号の重複を確認」を開くと、学籍番号・生徒名・紐付けアカウント数を確認できる。GET /api/central/duplicatesはローカルDBのみを読み、クルー・生徒には許可しない。個人情報は認証済み画面にだけ表示し、ログへ出さない。重複解消の自動削除・統合は行わない。

## 新規生徒の即時アカウント作成

中央連携有効時、管理者・セールスは生徒管理の「Notionから新規アカウント作成」を押せる。Notionへ登録しただけで自動実行されるWebhookではない。NOTION_TOKEN・NOTION_DATABASE_IDと対象DBの共有権限を維持する。従来の6プランを対象に、学籍番号をログインID、初期PW1111、初回変更必須で新規作成/既存アカウント連携する。

通常の中央管理DB同期とは別API（POST /api/notion/provision-accounts）で、中央DBに生徒がまだなくても作成できる。既存生徒の氏名・プラン・状態・手動ログインID・パスワード等はNotionで上書きしない。未作成の既存キャッシュについては現在の保存情報を使って作成を再試行する。学籍番号なし・重複・曖昧な紐づけはスキップする。

新規キャッシュはraw_data.source=notion_pendingとして「Notion受付・中央DB反映待ち」と表示する。中央DBに未反映の間は「同期対象外」にしない。予約ボタンも中央反映まで非表示。中央同期が学籍番号/Notion IDで照合すると同じアカウントを引き継ぎ、待機マークがcentralへ変わる。それ以後の更新・対象外判定は中央DBに従う。中央に反映されないままの待機レコードを自動失効させる期限は設けていないため、長期待機は運用で確認する。

両経路を単一プロセス内のキューで直列化し、同時実行の重複を防ぐ。複数インスタンス運用は引き続き対象外。支払いスプレッドシートの判定は変更しないため、アカウント作成だけで有料コンテンツへの利用可否が変わるわけではない。

## ダッシュボード成長ロードマップ

表示には中央管理DBのstudents.text_typeが「新」であることも必須。毎時/手動中央同期でraw_data.textTypeへ保存し、旧・未設定・中央未反映は非表示とする。test_seitoのみ専用手動設定のテキスト区分で確認できる（初期値は旧、Notion未連携に限定）。既存のプラン・1〜5ヶ月目条件はそのまま適用する。

スタンダードプラン・生徒プランのみ、レッスン開始月を1ヶ月目とする日本時間の暦月計算で1〜5ヶ月目に表示する。開始日なし・開始月前・6ヶ月目以降は非表示。18ヶ月分のX/YouTube目標表はすべて表示し、現在月を強調する。5ヶ月目には「目指せ、Live2Dデビュー！ 5ヶ月目の目標達成で、1回目の延長審査でLive2D獲得のチャンス！」を表示する。延長審査や報酬付与の自動処理は追加しない。

本人限定のGET /api/central/my-growthは既存SNSキャッシュの最新成功人数と取得日時を返す。新たなSNS API呼び出し・履歴保存は行わず、YouTube30日等の既存保持範囲を使う。未取得は0人扱いしない。目標0人の月は割合計算せず準備期間と案内する。test_seitoの手動プラン・開始日と既存テストSNS設定でも確認可能。

## test_seitoの手動設定

管理者は生徒用アカウント管理でtest_seito行の「生徒情報・レッスン日」を開き、氏名・学籍番号・契約プラン・ステータス・レッスン開始日、予約の日付・時刻・Tutor名を設定できる。Notion未連携かつログインIDがtest_seito、権限が生徒である既存アカウントに限定する。一般生徒は変更不可。ログインID・パスワード・SNS設定は変更しない。氏名と生徒プロフィールは通常の表示にも使い、学籍番号・予約はtest_student_settingsに隔離して保存する。予約は最大50件。日付は実在日、時刻はHH:mmで検証する。

手動設定後は中央同期なしでダッシュボードに手動予約を表示する。エントリープランで非表示、当月0/1/2件の案内、明日の予約で前日通知を確認できる。予約を全削除すると0件となる。設定を初めて保存するまでは通常の予約表示処理。Notionへ連携された場合は手動編集・手動予約表示を無効にして通常連携へ戻す。

## 診断ログと画面表示

同期開始・完了件数と、失敗時のstage/code/固定の案内文をログへ記録する。接続URL・パスワード・SQL・生徒情報・元の例外のmessage/stackは診断ログへ出さない。例：source_connect / ENOTFOUNDはホスト解決、source_tutors / 42703はTutor取得で不足列、42501は権限、TLS_MODE_MISMATCHはInternal URLのSSL設定を確認する。

手動同期の結果はボタン付近に継続表示する。応答が60秒を超えたら待機を解除するが、サーバーの同期を中断しない。再度手動同期を押しても既存の実行を共有する。status APIは最後の失敗理由・実行中状態を返すため、画面を再表示しても確認できる（診断状態はプロセスメモリで、再起動すると消える。最後の成功時刻はDBに保持）。本番の具体的原因はデプロイ後にこの診断結果で特定する。
